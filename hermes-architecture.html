How Hermes Works

A self-improving, multi-platform AI agent that runs any open or proprietary LLM via 200+ providers, executes 65+ tools, and operates across Telegram, Discord, Slack, WhatsApp and 15+ other platforms — on a $5 VPS or GPU cluster.

01 / System Overview

Hermes is built around a central Agent Core surrounded by four major subsystems: the multi-platform Gateway, a composable Tool Ecosystem, persistent Memory & State, and the Scheduler for automated jobs.

Agent Core
conversation_loop.py drives the LLM call → tool execution → re-prompt cycle. 3,900+ lines of production runtime.
Gateway
875KB multi-platform orchestrator. Holds an LRU cache of up to 128 live AIAgent instances with 1-hour idle TTL.
Tool Ecosystem
65+ tools self-register at import time. Parallel or serial execution based on destructiveness analysis.
Scheduler
File-lock cron. Gateway ticks every 60 s. Spawns fresh isolated AIAgent per job; never blocks the main loop.
Memory & State
SQLite WAL + FTS5 full-text search. Persistent SOUL.md / MEMORY.md / USER.md injected into every prompt.
MCP Integration
Hermes both hosts an MCP server (for Claude Code / Cursor) and consumes any external MCP server as tools.

03 / Request Lifecycle

End-to-end trace of a user message from Telegram through the gateway, agent core, tool execution, and back to delivery.

1

Platform Ingest — gateway/platforms/telegram.py

The TelegramAdapter.poll() long-polls the Telegram Bot API and receives an incoming message update. The adapter normalises it into a Hermes IncomingMessage and hands it to the GatewayRunner.

2

Session Resolution — gateway/session.py

GatewayRunner looks up (or creates) a session keyed by (platform, user_id, chat_id) in state.db. Sessions hold the Hermes conversation ID, platform-specific metadata, and a reference to the cached AIAgent if one is already warm.

3

Agent Cache Lookup — LRU Cache (max 128, 1 h TTL)

The gateway checks its LRU agent cache. A cache hit returns an existing AIAgent already loaded with credentials, tool schemas, and memory state — saving ~240 ms of init overhead. A miss triggers full agent initialization.

4

System Prompt Assembly — agent/prompt_builder.py

The prompt builder layers: base system instructions → SOUL.md (persona) → MEMORY.md + USER.md (persistent facts) → AGENTS.md (project context) → active skills → injected context files → FTS5 session-search recall snippets. The stable prefix is kept in Anthropic's server-side prompt cache.

5

LLM API Call — agent/transports/*

The selected transport (Anthropic, ChatCompletions, Bedrock, Codex) makes a streaming API call with the full message history and tool schema. The credential pool rotates API keys and handles 401 / 429 with per-key cooldowns and automatic failover.

6

Tool Call Parsing & Execution — agent/tool_executor.py

Tool call blocks are extracted from the LLM response. The executor groups them into parallel batches (reads, web searches, vision) vs. serialized paths (terminal writes, file mutations). Up to 8 workers run concurrently; results exceeding 5 KB are streamed to disk via tool_result_storage.py.

7

Re-prompt Loop — conversation_loop.py

Tool results are appended as an assistant message and the loop calls the LLM again. This repeats until the LLM emits stop_reason = "end_turn" or the 90-iteration budget is exhausted. Each turn the iteration budget and context size are re-evaluated.

8

Post-Turn Hooks

After the final response: (a) context compressor fires if history > 80 % of the window; (b) memory manager posts a nudge for memory review; (c) turn is saved to state.db; (d) if save_trajectories is on, a JSONL record is appended; (e) a skill may be auto-generated.

9

Response Delivery — gateway/delivery.py + platform adapter

The formatted response is sent back via the originating platform adapter. For Telegram this means splitting on the 4,096-char limit, sending chunks as separate messages, and optionally attaching inline keyboards for /retry, /new shortcuts. Delivery metadata is recorded in state.db.

10

Background Cron Tick — cron/scheduler.py

Independently, every 60 s the gateway calls cron.scheduler.tick(). Due jobs are loaded from jobs.json, a fresh isolated AIAgent is spawned per job (with protected toolsets disabled), the job prompt is executed, and the result is routed to the delivery target (Telegram, Discord, email, etc.).

06 / Memory Architecture

Hermes layers five distinct memory tiers, from ephemeral in-context history to durable procedural knowledge, all accessible via the session_search FTS5 index.

💡

SOUL.md · Persona

The agent's core identity and behavioral constraints. Injected first in every system prompt. Never compressed. Customizable per deployment.

🧠

MEMORY.md + USER.md

Persistent facts about the world and the specific user. Written by the memory tool. Automatically reviewed and pruned after complex turns (Hindsight plugin nudge).

📚

Skills (procedural)

Step-by-step procedures stored as markdown in ~/.hermes/skills/. Auto-created after complex tasks. Injected into the prompt by the memory manager.

💬

Session History · state.db

Full conversation history in SQLite with WAL mode. FTS5 virtual table enables the session_search tool to recall relevant snippets from past conversations.

🗜️

Compressed Context

When the active context window reaches 80 %, an LLM summarization pass compresses older turns into a compact summary block, preserving decision rationale.
